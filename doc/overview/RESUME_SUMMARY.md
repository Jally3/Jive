## 一、简历项目介绍（完整版）

**Jive — Flutter 跨端视频点播聚合播放器（个人项目）**

纯客户端、零后端的影视聚合 App，直连多家第三方资源站完成浏览、搜索、播放、缓存、下载全链路。基于 Flutter 实现 Android / iOS / macOS / Android TV 四端，自研本地代理播放与缓存体系，支撑边播边下、HLS 广告过滤、离线续播等能力。

**技术栈**：Flutter / Dart、Riverpod 3、video_player、flutter_js、HLS(m3u8)、本地 HTTP 代理、SharedPreferences / 文件存储

**核心亮点**：

- **多源聚合架构**：设计 `VodSourceAdapter` 协议层 + 源注册表，统一接入 MacCMS、AGE、欧乐、Syncnext 四类异构资源协议；基于 `flutter_js` 在端内实现 JS 插件运行时（桥接 `$http`/Cookie），可直接运行社区 Syncnext 插件，**新增插件源无需编写 Dart 代码**；以 `sourceId:sourceVideoId` 全局身份实现缓存、收藏、历史的跨源隔离，并支持全局/搜索/详情三级切源与失败原子回滚。
- **边播边下与缓存体系**：自研**本地回环 HTTP 代理**接管播放流量，解析并重写 HLS manifest，将播放、缓存、下载收敛为同一数据通路；`CacheManager` 实现 LRU+TTL 双维度淘汰、引用计数与写租约、**SingleFlight 并发请求去重**、基于 sha256 的 ContentKey 寻址及签名 URL 归一化，保证带时效参数的分片链接稳定命中缓存。
- **HLS 广告过滤**：自研广告分片识别算法（夹心中插检测 + 播放节奏异常识别），重写 m3u8 并保留 `DISCONTINUITY` 边界；设计源/过滤后双时间轴映射（TimelineMapping），配合 seek 时钟冻结与断点吸附重试，解决广告段拖动进度漂移问题。
- **下载引擎**：实现任务持久化、并发许可池、暂停/恢复/**断点续下**与下载速度采样；下载产物复用缓存配额与解析链路，支持离线优先续播。
- **播放器体验**：构建完整播放状态机（地址过期重试、前后台切换、资源释放）；实现手势控制体系（长按倍速、横滑 seek、纵滑亮度/音量）、自绘缓冲区间进度条、按影片记忆的跳过片头/片尾、Wi-Fi/蜂窝差异化分片预取。
- **多端兼容**：手机/平板自适应布局之外，完成 Android TV leanback 适配（遥控器确定性焦点导航、播放按键映射，经 MethodChannel 识别设备）；通过内置 ISRG Root X1 证书兼容 Android 6 的现代 TLS 连接。
- **工程质量**：Feature-first + 轻量 Clean Architecture 分层，页面层零直接 IO；测试覆盖 Adapter、HLS 解析、广告过滤、缓存淘汰与下载管理等核心逻辑。

## 三、面试追问深度准备

### 问题 1：本地代理为什么能统一「播放 / 缓存 / 下载」三条数据通路？

**一句话回答**：播放器只认 URL，我把它要访问的 URL 全部换成 App 内本地代理的地址，于是所有分片流量都必须经过我写的一个入口函数；缓存命中、回源、写盘、预取、下载都只是这个入口的不同调用方。

**展开讲（按这个顺序）**：

1. **播放器的约束**：`video_player` 只接受一个 URL，不支持「先查缓存再决定给什么」的钩子。直接给源站 URL 就完全失去了对流量的控制。
2. **代理接管**：App 启动时绑定 `127.0.0.1` 随机端口的 `HttpServer`（`LocalProxyServer`）。播放会话建立时解析源 m3u8，把 manifest 里每个分片/密钥 URL 改写成 `http://127.0.0.1:<port>/play/<token>/res/<resourceId>`，再把改写后的 manifest 通过 `/play/<token>/index.m3u8` 喂给播放器。播放器后续的**每一个**请求都落到代理上。
3. **token 路由表**：`ProxySessionRoute` 按 token 保存 `resourceId → 源站 Uri` 映射、会话请求头（Referer/UA 等）和一个 `ResourceFetcher`。多个播放会话互不干扰；会话结束 `unregister`，路由立即失效。
4. **唯一数据入口 `ResourceFetcher.fetch`**：代理收到分片请求后调它，逻辑是标准的 cache-aside + write-through：
   - 查缓存索引（ContentKey sha256 寻址）→ 命中则把本地文件流回给播放器，零网络；
   - 未命中则回源拉取，响应流一边转发给播放器、一边写 `.part` 临时文件，校验通过后 rename 为正式文件并 `commitResource` 入账；
   - 缓存不可用时旁路（bypass）直连，播放不被缓存故障拖死。
5. **三条通路收敛**：
   - **播放**：播放器经代理拉流，隐式写缓存；
   - **边播边下（预取）**：`SegmentPrefetcher` 不经过 HTTP，直接调同一个 `fetcher.fetch` 提前抓未来 N 秒的分片（Wi-Fi 300s / 蜂窝 120s 窗口），抓完的分片播放器再请求时就是缓存命中；
   - **显式下载**：`DownloadTaskManager` 同样调 `fetcher.fetch` 拉全部分片，产物就是缓存条目，标记 `downloadOrigin` 不被 TTL 淘汰。
   - 三者只是**触发者**不同，「命中判定 / 回源 / 写盘 / 配额」只有一份实现。
6. **代理还白捡了几个能力**：广告过滤（manifest 层删分片，播放器无感知）、加密 key 缓存、响应头白名单转发、HEAD content-type 嗅探、在途请求计数（`activeReads`）保证关会话时不截断正在传输的响应。

**可能的追问**：
- *为什么不用播放器自带缓存或 Dio 拦截器？* —— 播放器没有缓存钩子；Dio 拦截器只能管自己发出的请求，管不到播放器 native 层发的 HTTP。代理是唯一位于播放器和网络之间、且完全可控的位置。
- *性能开销？* —— 回环代理不经网络栈出设备，延迟可忽略；数据是 stream 透传（`addStream`），不做整包缓冲，内存占用与直连一致。
- *iOS 允许吗？* —— 允许，访问的是 loopback，ATS 对 127.0.0.1 不强制 HTTPS；源站请求仍全部走 HTTPS。

### 问题 2：SingleFlight / 写租约 / 引用计数分别解决什么并发问题？

**背景先说清**：Dart 是单事件循环，但一个分片的生命周期里有大量 `await`（网络、文件 IO），多个调用方的异步任务会交错执行。缓存元数据（索引、字节计数、配额）如果没有临界区，就会出现经典的竞态。我用了三个原语分别解决三类问题：

**① SingleFlight —— 重复请求去重（防重复回源 + 重复写盘）**

- 场景：播放器请求分片 X 的同时，预取器也在抓分片 X。若各自回源：浪费一倍带宽，且两个写者写同一个 `.part` 文件会互相截断/污染。
- 实现：`SingleFlight` 内部维护 `key → Future` 映射，第二个同 key 调用直接返回**同一个 Future**，请求结束后移除 key。
- 关键细节：HTTP 响应体是**单订阅流**，两个消费者不能共享同一个 stream（后到者会拿到已被消费的流，直接卡死——这是我实际踩过的起播卡死 bug）。所以策略是：播放路径发现某分片正在被后台预取时**不 join**，而是独立回源保证起播，缓存写入只提交一次；反过来预取发现播放路径在抓则主动让行（`skipped`），下轮调度再补。

**② WriteLease（写租约）—— 配额预留（防空间超卖）**

- 场景：两个并发下载任务各自检查「剩余空间 > 我的大小」，都通过，然后一起写爆磁盘。
- 实现：写盘前必须 `reserve(entryKey, bytes)`：把字节数计入 `_pending`（已预留未提交），配额判定用 `已用 + 所有在途预留 ≤ 配额`。空间不足时先跑 TTL 过期淘汰，再按 LRU（partial 条目优先于 complete）淘汰别的条目；仍不够则 reserve 失败、任务降级。写完 `commitResource` 把预留转为实际占用，失败/取消 `cancel` 释放预留。下载中发现实际更大可 `ensureCapacity` 扩容重检。
- 配额本身也动态计算：磁盘可用空间 + 已用缓存，再留 5%（2–10GB 封顶）安全余量。

**③ CacheRef（引用计数）—— 在用数据保护（防边播边删）**

- 场景：播放到第 30 分钟时，TTL 清理或 LRU 淘汰或用户「清空缓存」把当前会话的分片目录删了，播放直接断流。
- 实现：播放会话开始 `acquire(entryKey)` 拿 `CacheRef`，期间 `deleteEntry` / `clearAll` / TTL 淘汰看到引用数 > 0 一律 blocked/skip；会话结束 `release`。代理层另有 `activeReads` 统计在途 HTTP 读，关会话时等读排空。

**配套的崩溃一致性**（也是加分点）：写入走 `.part` 临时文件 → 校验（字节数 + TS/fMP4 魔数，加密分片跳过魔数）→ rename 提交 → 更新 `state.json`。启动时 `reconcile` 双向清扫：正向按记录核对文件（大小不符降级、缺失移除），反向按文件找记录（孤儿目录删除、残留 `.part` 清理、rename 后崩溃遗留的完整文件补建记录）。所有元数据变更经一个尾链实现的 `AsyncMutex` 串行化，索引保存再做 800ms 节流。

**一句话总结**：SingleFlight 管「同一个请求别发两次」，WriteLease 管「空间别超卖」，CacheRef 管「在用的别删」。

### 问题 3：广告过滤算法怎么判定一个分片是广告？

**先说边界（诚实且体现理解）**：只能过滤**清单级可分离的广告**——广告是独立分片、且 m3u8 里带 `#EXT-X-DISCONTINUITY` 边界标记（SSAI 或切片打包广告）。硬编进正片 TS、清单无断点的广告，在 manifest 层面没有任何信号，无法去除（过滤报告里也会明确提示这一点）。

**判定框架**：不依赖单一规则，而是 **7 条启发式规则投票**，每条规则输出一个广告块（起止分片 + 置信度），最后合并重叠块。规则按置信度从高到低：

| 规则 | 置信度 | 判定依据 |
| --- | --- | --- |
| `explicit` 显式标记 | 1.0 | 分片 URL 路径含 `/ad/`、`/ads/`、`/adjump/`、`/gg/`、`/gdt/`、`/zj/` 或 query 含 `adjump` |
| `shortCluster` 短分片簇 | 0.8 | 连续 ≥5 个「短分片」（时长 < 基准×0.7），且平均时长 < 基准×0.5。广告为控体积通常切得更碎 |
| `discontinuityDuration` 断点短组 | 0.7 | 按 DISCONTINUITY 分组，组内平均时长 < 基准×0.65 且总长 ≤45s |
| `hostCluster` 异主机簇 | 0.6 | 主 CDN 主机分片占比 >70% 时，落在非主主机上的连续分片（≤15 片、≤45s）——广告常走第三方广告 CDN |
| `cadenceDwarf` 节奏侏儒 | 0.65 | 针对密集断点打包器（如电影天堂系，每 ~5 个正片分片打一个断点）：统计发现某组分片数占比 ≥70%，即为「正片节奏」；显著小于该节奏、连续出现且总长 6–45s 的组判为广告；片尾残段不杀 |
| `midRollSandwich` 夹心中插 | 0.6 | 中间断点组时长 12–90s，且前后两组都是 ≥120s 的长正片组——中插广告的典型结构；不碰首组和尾组（片头/片尾不轻易动） |
| `dwarf` 结构侏儒 | 0.5 | 中间断点组 ≤8 片且 ≤45s，被两个 ≥15 片的长组夹着 |

- **基准时长 baseline**：所有分片时长的**中位数**（比均值抗极值，广告本身不会把基准带偏）。
- **合并策略**：所有候选块按起点排序，相邻/重叠块合并，置信度取较高者；再从 playlist 删除对应分片重写 m3u8。
- **阈值思路**：所有规则都要求广告块**短**（≤45/90s）且正片上下文**长**（≥120s 或 ≥15 片），用结构性不对称压低误杀——把一段正片误删的代价远大于漏过滤一段广告。

**过滤之后的两个工程难点**（这才是深度所在）：

1. **时间轴错位**：删掉 60s 广告后，播放器时间轴和源时间轴不一致了——用户历史进度、拖动条、续播位置全部对不上。解法是 `TimelineMapping`：记录每个被删区间在源时间轴上的 `[start, end)`，提供 `sourceToFiltered` / `filteredToSource` 双向换算（遍历区间累加偏移量），进度保存用源时间轴、播放器内展示用过滤后时间轴。
2. **解码器连续性 + seek 漂移**：删分片会让相邻正片分片的时间戳/编码参数不连续，所以重写时在广告缝**保留 `DISCONTINUITY` 标记并移除 PDT（Program Date Time）空洞**，让解码器正常重置。另外广告段消失后，native 播放器的实际落点和 UI 尺子会有偏差，拖动到广告缝附近时进度会被「放大」；解法是 seek 时钟冻结（记住可播时长、拖动期间冻结尺子）+ 检测到 native 落点吸附在断点上时自动重试到正确位置。

**可能的追问**：
- *误杀怎么办？* —— 规则全部是保守阈值 + 置信度设计；过滤结果在播放页状态圆点可见，长按展示每条规则命中明细（AdFilterReport），可观测、可回放。规则版本号（adfilter-v3）随缓存条目持久化，规则升级后旧缓存可判定失效。
- *为什么不用服务端方案/AI？* —— 零后端约束下只能在客户端做；manifest 级启发式规则零网络开销、可单测（我为每条规则写了构造 playlist 的单元测试），且不依赖内容识别。

## 四、其他可能被问到的点（速记）

- **为什么用 Riverpod？** 统一状态管理 + DI，手写 Provider 不引入 codegen；列表/搜索用 AsyncNotifier 天然承载 loading/error；全局源用 Notifier 持久化到 SharedPreferences。
- **flutter_js 跑插件怎么保证安全/稳定？** JS 运行在隔离的 JS 引擎沙箱里，`$http` 是我注入的桥（强制 HTTPS、超时、header 白名单），插件脚本按源缓存会话；网络不可达该源加载失败但不影响其他源——未知 adapterType 直接忽略，整张源列表不失效。
- **搜索多源并发怎么控？** 1 当前源 + 最多 3 备用源并发探测，每源独立分页/错误态；600ms 防抖 + generation 代次隔离，旧请求结果即使晚回来也被丢弃；「关键词+源+页码」结果缓存约 7 分钟。
- **跨源切换怎么保证不错乱？** 资源全局身份 `globalId = sourceId:sourceVideoId`，缓存键、收藏、历史、Widget Key 全部用它；详情切源是「探测 → 用户确认 → 原子替换，失败回滚保留旧详情」。
- **Android 6 兼容做了什么？** 老设备不信任新 ISRG Root X1 根证书，启动时把内置 PEM 追加进 SecurityContext；另外锁定多个插件的 Android 实现版本，规避依赖把 minSdk 提到 24。
