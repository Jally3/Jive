# 边播边下 与 广告过滤 —— 纯原理讲解

> 本文不涉及任何具体代码,只讲原理、流程和设计取舍。
> 适合讲给有技术背景、但不了解流媒体细节的朋友。

---

## 〇、先花两分钟搞懂 HLS,后面一切都顺理成章

HLS(HTTP Live Streaming)是现在网络视频最主流的传输方式。它的思想极其朴素:

**把一整部电影切成几百个小片段,每个片段几秒,再配一个"目录文件"记录片段清单。**

- 目录文件叫 **m3u8**,本质是一个文本文件,长这样:

```
#EXTM3U
#EXT-X-TARGETDURATION:10
#EXTINF:4.000,
http://cdn-a.com/movie/0001.ts
#EXTINF:4.000,
http://cdn-a.com/movie/0002.ts
...（几百行）
#EXT-X-ENDLIST
```

- 每一行 `#EXTINF:4.000,` 表示"下面这个片段时长 4 秒";
- 每个 `.ts` 是一个独立的视频切片(MPEG-TS 格式),里面装着几秒的音视频数据;
- 播放器的工作方式:先下载目录,然后按顺序逐个下载切片、逐个播放。

这个结构带来三个对极有利的特性:

1. **粒度可控**——视频不是一个整体,而是几百个独立小文件,下载、缓存、替换都可以按片段进行;
2. **目录是文本**——可以随意改写、删减、重组,而且目录本身极小(几十 KB),改起来零成本;
3. **每个切片自带时间戳**——TS 格式的数据包里嵌着 PTS(呈现时间戳),播放器靠它对齐音画和进度,这给后面"识别广告"提供了最真实的依据。

记住这三点。后面所有的设计,都是在利用这三个特性。

## 一、整体思路:在 App 内部开一个"本地电视台"

### 传统做法的问题

想实现"边播边下、看过的不再耗流量、下次秒开",最笨的办法是:播放器播它的,下载器下它的,两条路各走各的。问题马上来了:

- 播放器永远走网络,本地缓存下完了它也不用,流量照烧;
- 想让播放器用上本地片段,就得中途给它换源,一换源就黑屏、回退、进度丢失;
- 有些系统播放器(比如苹果的 AVPlayer)对本地文件播放还有很多古怪限制,直接给它一个本地 m3u8 它甚至拒绝播放。

### 本项目采用的架构:本地 HTTP 代理

思路转换一下:**不让播放器直接碰网络,在 App 内部启动一个只对本机开放的微型 HTTP 服务器,让播放器从头到尾都"以为自己在联网看一个固定地址"。**

```
┌──────────────┐        ┌─────────────────────┐        ┌──────────┐
│              │ 请求目录 │                     │ 已下载→ │ 本地磁盘  │
│   播 放 器    │───────→│  本地代理服务器        │────────→│ (片段缓存)│
│              │ 请求片段 │  (127.0.0.1:某端口)  │        └──────────┘
└──────────────┘        │                     │ 未下载→ ┌──────────┐
                        └─────────────────────┘────────→│ 远端 CDN  │
                                 ↑                      └──────────┘
                        ┌─────────────────────┐
                        │   后台并发下载器       │
                        │ (按顺序把片段拉到本地) │
                        └─────────────────────┘
```

三个角色:

1. **播放器**——只认一个地址:`http://127.0.0.1:端口/play.m3u8`。它完全不知道本地缓存的存在;
2. **本地代理服务器**——收到目录请求时,动态生成一份"混合目录";收到片段请求时,查一下本地有没有:有就直接把磁盘文件吐回去(毫秒级),没有就回一个"临时跳转"让播放器去远端取(等价于直连,只多一次本机握手);
3. **后台下载器**——用户开始播放的同时,按顺序把所有片段并发下载到本地磁盘,每下完一片就通知代理一声。

**这个架构最妙的地方:播放器自始至终只播一个 URL,永远不需要"换源"。** 所谓的"在线切本地",根本不是切换播放器,而是代理服务器在背后悄悄改了数据来路。这是无缝体验的根基。

另外:直播流(没有结束标记、目录会不断变长的那种)天然不适合边播边下,系统会在解析目录时识别出来,直接保持纯在线播放,不走这套流程。

## 二、边播边下的完整生命周期

### 阶段 1:决策(点开视频的一瞬间)

用户点击播放,系统先判断这个视频在本地磁盘上有没有"遗产":

- **缓存目录怎么找**:用视频地址算一个哈希值作为目录名。这里有个细节——视频地址后面通常带着一串时效性的 token 参数(防盗链签名,几小时就变),**算哈希前必须把这些参数剥掉**,否则同一部电影每次地址都不同,缓存永远命中不了。
- 找到缓存目录,再检查完整性:
  - 片段齐全、全部校验通过 → 跳过在线阶段,直接进代理模式(秒开);
  - 只有一部分 → 边播边下,已下载的部分直接用;
  - 没有 → 全新开始,边播边下。

### 阶段 2:双轨启动(前几十秒)

对于没有完整缓存的视频,系统同时做两件事:

- **轨道 A:播放器立刻按原始网络地址开始在线播放。** 用户零等待,和没有缓存功能时体验完全一样;
- **轨道 B:后台下载目录、解析、剥离广告(下文第四节),然后开始下载片段。** 第 0 个片段最优先下载——它是切换轨道的入场券。

### 阶段 3:下载调度(贯穿全程)

后台下载器的工作方式:

- **并发下载**:同时下载多个片段(默认 5 路,网络好可以自动加码),连接层走 HTTP/2 复用;
- **有序优先**:总体按片头到片尾顺序下载,播放器前进时,当前位置后面的几片会被临时提到最前面——保证"下载始终跑在播放前面";
- **失败重试**:失败的片段进专门的重试队列,限制同时重试的数量,避免失败后风暴式重发把网络打满;
- **磁盘满了怎么办**:自动找出缓存里最久没看的一整部影片删掉,腾出空间再写,循环直到写入成功;
- **防串台**:每次启动下载生成一个"会话编号",所有下载任务都带着这个编号。用户中途退出换片时,旧编号作废,旧任务的结果就算回来了也会被直接丢弃——防止上部电影的片段写进这部电影的缓存里;
- **断网与恢复**:下载进度持久化在磁盘上(目录里存一份状态文件),App 重启后扫描目录、逐片校验,能用的接着用,坏的标记重下。

### 阶段 4:切换时机(关键设计:不等到全下完)

什么时候把播放器从"纯在线"切到"代理模式"?直觉答案是"全下完再切",但这是错的——那样用户看到一半才享受到本地缓存,意义大打折扣。

实际策略:**只要"当前播放位置"和"未来 10 秒"对应的片段都已经在本地,就可以切了。** 因为:

- 切换后,正在播的和马上要播的片段都能从本地读,播放不会断;
- 更后面的片段就算还没下完,代理会自动跳回远端取,无缝兜底;
- 下载速度通常远快于播放速度(下载 4 秒的内容往往只要零点几秒),"下载在前、播放在后"的队列会一直保持。

也就是说,用户正常看几十秒之后,就已经神不知鬼不觉地切换到混合模式了。

### 阶段 5:稳态与终态

- **混合态**:一部分片段走本地,一部分走网络。随着下载推进,本地命中比例越来越高,流量消耗持续下降;
- **完成态**:全部片段下完,目录里所有片段都指向本地。此后拖动进度条到任何位置都是毫秒级响应,零流量,断网也能看;
- **下次再看**:同一部电影(哈希相同)直接命中完整缓存,跳过所有阶段,秒开。

## 三、无缝衔接的四个关键技术

"在线片段和本地片段拼在一起,播放不卡、不跳、不闪",靠的是下面四层机制。

### 技术 1:混合目录——时间轴完全一致,只有地址不同

代理生成目录时遵循一条铁律:**片段的数量、顺序、每段标注的时长、不连续标记的位置,全部和原始目录一模一样;唯一改写的只有片段地址。**

改写规则是统一的:不管下没下载,所有片段地址都改写成 `http://127.0.0.1:端口/segment_序号.ts`,由代理在收到请求时再决定是读磁盘还是跳远端。

为什么不直接"已下载的写本地文件路径、没下载的写原网址"?因为播放器对一份目录里混用多种协议很敏感(尤其是 FFmpeg 内核的播放器),地址风格统一可以让播放器行为完全一致,排障时也能清楚看到每个片段到底命中了本地还是网络。

对播放器来说,它拿到的就是一份**静态的、完整的、普通的点播目录**。视频数据本身是同一条编码流,不管来自磁盘还是网络,里面的时间戳都是连续的——**"无缝"不是自己拼出来的,而是原始流本来就是连续的,只要不破坏目录结构,播放器天然无缝。**

### 技术 2:位置挂起与恢复——切换播放源时记住"看到哪了"

有一种情况必须真的换播放地址:从"在线直放"切到"代理播放"。换地址意味着播放器重新打开一个流,默认会从头开始。解法分三步:

1. **切换前挂起**:记下两个信息——当前播放到第几秒、当前是播放中还是暂停;
2. 换地址,等新流加载到"可以播"的状态;
3. **恢复**:跳到刚才记下的位置,并按之前的状态继续播或保持暂停。

用户感知到的只是一次极短的缓冲,进度条纹丝不动。

这里还防了一个很隐蔽的坑:如果切换的瞬间正好在播广告,而广告片段的时间戳是乱的,播放器报告的"当前位置"可能突然变成 0——轻信它就会跳回片头,用户会以为见鬼了。所以系统另外维护一个"最近一次确认可信的播放位置",读到的位置明显异常时(比如从几百秒突然掉到 0),用可信位置代替。

### 技术 3:双时间轴换算——剥掉广告后,进度条对不上了怎么办

这是最容易被忽略、也最体现功力的一点。

- 在线直放阶段,播的是**原始目录,广告还在里面**,所以进度条走的是"含广告时间轴";
- 切到代理模式后,目录里的广告**已经被剥掉**,整条时间轴变短了。

假设用户在 30:00 的位置切换,而这之前被剥掉了两段共 90 秒的广告。如果直接在新目录里跳到 30:00,实际会落到正片 31:30 的内容上——用户会发现剧情跳了。

解法:系统会记录每条被剥广告在**原始时间轴**上的位置和时长。切换时做一道减法:

> **新位置 = 原位置 − 之前所有广告的累计时长**
> (如果用户正好停在广告中间,就钳到这条广告被剥掉后对应的接缝处)

一道换算,两条时间轴对齐,进度条、剧情全部连续。

### 技术 4:目录快照锁定——照顾"敏感"的播放器内核

不同的播放器内核对"目录变化"的容忍度完全不同:

- 苹果原生内核(AVPlayer)很健壮:每次来要目录,给它最新版就行,它能平滑地处理片段地址变化;
- FFmpeg 内核很敏感:下载比播放快得多时,目录会频繁重生成、片段地址一片片地从网络变成本地。FFmpeg 会被这种变化扰乱内部时钟(实测音视频偏移能漂到负十几秒),然后疯狂丢帧,画面卡成 PPT。

解法:**对敏感内核,目录首次生成后就"锁定"不变**,它每次来要都返回同一份快照。快照只在两种时机整体换新:每多下载完一小批片段(比如 5 片),或全部下载完成时。相当于"每隔一段时间给它一张当时状态的稳定照片",而不是一份一直在它眼前变化的清单。

换内核等于换一套行为策略,这些策略被隔离在代理层,上层逻辑不用关心。

## 四、广告过滤:为什么广告可以被"算"出来

### 先理解广告是怎么进去的

这类视频站的广告不是压在视频文件里的(那就神仙难救了),而是**在目录里插了额外的片段行**。一段原始目录长这样:

```
#EXTINF:4.0,
movie/0099.ts        <- 正片
#EXT-X-DISCONTINUITY          <- "以下内容与前文不连续"标记
#EXTINF:1.7,
ads/xx01.ts          <- 广告片段
#EXTINF:1.7,
ads/xx02.ts          <- 广告片段
#EXT-X-DISCONTINUITY
#EXTINF:4.0,
movie/0100.ts        <- 正片继续
```

`#EXT-X-DISCONTINUITY`(下称"断点标记")是 HLS 协议里的标准标签,意思是"后面的片段和前面的不是同一条编码流,时间戳、编码参数可能对不上"。广告插播系统(SSAI,服务端广告插入)在拼目录时,理论上应该在广告前后打这对标记。

**也就是说:广告在文件层面只是目录里的一些行。只要能在几百行里认出哪些是广告行,删掉它们再交给播放器,广告就消失了——根本不需要碰视频数据本身。**

剩下的问题只有一个:怎么认?而"认"的底气来自一个事实:

> **正片是一整条流水线产出的,高度规整;广告是另一个世界的东西,混进来时总会在某个维度上露馅。**

系统一共用了 **1 条明牌规则 + 6 层静态分析 + 1 层运行时校验**。静态分析只看目录文本本身(零下载成本),运行时校验用真实视频数据做最终裁决。总哲学是八个字:**宁可漏过,不可误伤**——误删正片比漏掉广告糟糕一百倍,所以每一层都设了严格的触发条件,证据不足就整层放弃,绝不硬猜。

### 规则层:明牌标记

最简单的情形:有些片源在广告片段的地址里直接写着 `adjump`、`/ad/` 这类字样。字符串一匹配,直接删。这种"明牌"广告还会被记录位置和时长,供第三部分的双时间轴换算使用。

### 算法一:帧率节奏指纹

**规律**:正片是同一台编码器、同一个帧率压出来的。假设正片是 25fps,那么每个片段的时长必然是帧间隔(0.04 秒)的整数倍——4.000、4.040、3.960……**全部精确落在 0.04 的网格上**。而广告是广告公司自己的机器压的,往往是 30fps,时长落在 0.0333 的网格上。

这个特征极难伪装:广告片段可以改名、可以放在同一个域名下,但它的"时长指纹"是编码那一刻就定死的。

**做法**:

1. 先按断点标记把几百个片段分成若干"块";
2. 统计全体片段时长在 24/25/30 三种常见帧率网格上的贴合度。如果绝大多数片段(90% 以上)都贴合同一个网格,这个网格就是"正片指纹",可以继续;如果乱到找不出主导网格,说明这片源本身就不规整,算法放弃;
3. 逐块打分:某个块如果大量片段"脱网"(不贴合正片指纹),却高度贴合另一种帧率的网格,而且整块总时长很短(30 秒以内),就是广告嫌疑人;
4. 嫌疑人左右的邻居块如果也贴合那个异类帧率(或者是个几秒的小片头),一并算进来——广告常被拆成相邻的几小块;
5. 最后整体复核一遍:连续区间总时长不超过 45 秒、脱网片段足够多、异类帧率贴合度足够高,全部通过才真正删除。

### 算法二:域名聚类

**规律**:跨域投放的广告。正片几百个片段都来自 `cdn-a.com`,广告片段来自 `ads-b.com`——广告平台自己的服务器。

**做法**:统计全部片段的域名分布。如果某一个域名占比超过 70%,具有压倒性的"正片资格",就把零星的异域片段删掉。占比不够就放弃——很多良心站会用多个 CDN 轮询加速,域名本来就分散,不能误伤。

### 算法三:文件序号跳变

**规律**:同一台服务器上,正片片段的文件名通常是连续编号的:`0001.ts`、`0002.ts`……广告注入时,文件名序号会突然跳到另一个数段,比如 `98765.ts`。

**做法**:提取每个文件名末尾的数字,沿着目录顺序走,相邻序号一旦跳变超过 1000 就切一刀,把目录分成若干"连续段"。正常情况只有一段;出现多段时,最大的那段是正片,**又小又孤立(少于 30 段、不足最大段三分之一)的段**判为广告。前提:80% 以上的文件名都能提出数字——很多站用哈希随机命名,这招直接不适用,放弃。

### 算法四:断点分块 + 时长对比

**规律**:正规的广告插入会打断点标记,而且广告片段为了快速起播,单段时长通常压得很短(正片 4 秒/段,广告 1.7 秒/段)。

麻烦在于:有的插播系统会把一条广告切成好几小块,每块都单独打断点标记,单看每一小块可能不够"罪证确凿"。

**做法(两道阈值)**:

1. 按断点标记分块,算出每块的平均段时长,取全体中位数作为"正片片长基准";
2. **宽松线(基准的 85%)**:先把所有偏短的相邻块"合并"成候选区——解决广告被拆碎的问题;
3. **严格线(基准的 65%,且合并后至少 2 段)**:合并后的整体仍然显著短,才定罪。

先宽后严:宽是为了把碎片化的广告拼回原形,严是为了确保不误判。

### 算法五:短片段滑动聚类

**规律**:对付"不守规矩"的广告——前后没打断点标记,算法四失效。但物理特征还在:广告仍然是一长串短片段。正片里当然也有短片段(剪辑点、场景切换处),但**几乎不会连续出现 3 个以上**。

**做法**:用滑动窗口扫全片,短于基准 70% 的片段标为"短";连续短片段聚成一簇(允许中间夹 1 个正常片段,防止漏网);一簇必须**至少 5 个连续短片段、且平均时长不到基准的一半**,才判广告。阈值刻意卡得极严:正片的场景切换凑不出"连续 5 段都不到一半片长"的形态,所以这一层几乎零误伤。

### 算法六:结构上的"侏儒块"

**规律**:对付最"贼"的一类广告——和正片**同域名、同帧率、片长也正常**,前面五层全部漏掉(真实案例:某片源在正片 28 分钟处插了一个只有 4 段的广告块,每段时长 3~7 秒,帧率网格和正片完全一致)。

但它有一个怎么都藏不住的结构特征:**它被前后两个断点标记精确包裹着,自身极小(个位数片段、总长几十秒),而左右邻居都是几百段的庞然大物。** 一条两小时电影的正片块有上千段,广告块夹在中间就像两个巨人之间的侏儒。

**做法**:

1. 按断点标记分块后,用全体块大小的中位数定一个"大块"基准(中位数的四分之一,且不低于 30 段,防止本身就很碎的片源误判);
2. 只检查**中间**的块——第一个和最后一个块永远豁免,因为真实的片头(logo、版权声明)和片尾(预告)天然就是小块,是误伤重灾区;
3. 三个条件同时满足才定罪:**自身不超过 8 段、总长不超过 45 秒、左右邻居都是大块**。

### 算法七:运行时 PTS 时间戳校验(终极裁判)

前面六层都在分析"目录文本",文本是可以伪装的。这一层用的是**视频数据本身**,也是整个体系里最优雅的一招。

**背景知识**:每个 TS 片段的数据包里都嵌着 PTS(呈现时间戳),告诉播放器"这段画面应该出现在影片的第几秒"。正片从头到尾是同一条编码流,PTS 必然连续:第 99 段结尾在 396 秒,第 100 段开头就在 396 秒附近。

**规律**:动态插入的广告有自己独立的媒体时钟。广告的 PTS 不从 396 秒开始,而是从 0 秒(或它自己世界里的某个值)开始;**而广告播完之后,正片的 PTS 会神奇地从 396 秒原样接上**——仿佛广告从未存在过。因为正片文件本身没有被重新编码,它的内部时间戳不受目录里插了什么影响。

于是一个几乎不可能误伤的双重判据出现了:

> 某一块的开头和正片预期位置**突然跳变(差 30 秒以上)**,
> 同时这块结束后的下一块又**完美复位(误差 2 秒以内)**——
> 中间这块就是广告。

"跳变 + 复位"必须同时成立:只跳变不复位可能是片源本身的时间戳风格,只有"跳出去又精确跳回来"才是插入物的铁证。

**做法**:后台每下载完一个片段,顺手解析它的 TS 包头(TS 是固定 188 字节一个包、按同步字节对齐,很容易在二进制里找到第一个视频帧的时间戳),记下该片段的起始 PTS。随着下载推进,不断对分块做上面的双重判定。就算目录里完全没打断点标记,也能靠 PTS 跳变自己切出"可疑块"再判定。

最妙的是:这一层是**运行时持续工作**的。哪怕前六层全部漏掉,广告在播放途中被 PTS 校验抓出来,系统会立即更新目录把它剔除——观众可能刚看到半秒广告,它就消失了。

### 为什么广告商对抗不了这套体系

每一层单独看都有办法绕过:改文件名(绕算法三)、同域投放(绕算法二)、同帧率重编码(绕算法一)、不打断点标记(绕算法四)……但要同时绕过所有层,广告必须做到:**同域名、同帧率、连续编号、正常片长、不形成小孤块、PTS 还要和正片严丝合缝地接上**——而最后一条是死穴:真要做到 PTS 无缝,就得把广告和正片拼起来重新编码,那"动态插入"这件事本身就失效了,等于广告被压进了正片,成本完全不可同日而语。

|---|---|---|---|
| 明牌规则 | 地址里写着 ad/adjump | 字符串匹配 | 只删明确标记的 |
| 1 帧率节奏 | 正片时长落在同一 fps 网格 | 主导网格 ≥90%;块内大量脱网且贴合异类网格;总长短 | 找不出主导网格就放弃;删除前整体复核 |
| 2 域名聚类 | 广告来自异域服务器 | 主导域名 >70%,删零星异域 | 占比不足整层放弃(防多 CDN 片源) |
| 3 序号跳变 | 广告文件名序号跳到别的数段 | 跳变 >1000;小段 <30 且不足最大段 1/3 | 80% 能解析出数字才启用 |
| 4 断点+时长 | 广告被断点包裹且片长短 | 宽 85% 中位数先合并,严 65% 再定罪 | 先宽后严两道闸 |
| 5 短片段聚类 | 广告是连续一长串短片段 | 连续 ≥5 段且均值 <50% 基准 | 阈值极严,宁漏勿错 |
| 6 结构侏儒块 | 广告是夹在巨人块间的小块 | ≤8 段、≤45 秒、两侧都是大块 | 首尾块豁免,保护片头片尾 |
| 7 PTS 校验 | 广告有独立时钟,正片会复位 | 跳变 ≥30 秒 + 复位误差 ≤2 秒 | 双重判据必须同时成立;基于真实流数据 |

## 六、这套设计里值得带走的通用经验

1. **代理模式是"边播边下"最干净的解。** 让消费端(播放器)始终面对一个不变的接口,把"数据从哪来"的复杂度全部藏在代理背后。播放器不需要为缓存写一行特殊逻辑。
2. **不要破坏消费端依赖的格式不变量。** 混合目录和原始目录在结构上逐行一致(时长、顺序、标记),只改地址。只要不变量守住,"无缝"是免费的,不需要任何拼接技巧。
3. **状态切换 = 挂起 + 恢复。** 换源、换模式这类"打断重来"的操作,先记下位置和状态,就绪后原样恢复,用户就无感。再补一个"最近可信值"兜底,防异常瞬时值。
4. **启发式识别的可靠性来自"多重判据 + 放弃机制"。** 每层算法都有"证据不足就整层不动"的退路,以及删除前的最终复核。宁漏勿错,因为误伤的代价远高于漏过的代价。
5. **最硬的特征来自数据本身,而不是元信息。** 文本特征(域名、文件名、时长)都能被对抗;流里的时间戳对抗不了——伪装它的代价等于放弃攻击本身。做检测时,尽量往下层数据找特征。
6. **不同下游要隔离差异策略。** 同一个代理,对健壮的内核实时刷新,对敏感的内核给锁定快照。差异收敛在一处,上层保持简单。
7. **并发任务用"会话编号"防竞态。** 换片、退出、重试并发交错时,给每次会话发个编号,旧编号的任务结果直接作废,比到处加锁可靠得多。
